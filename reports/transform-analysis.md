# Transform forensics: can a missing `WorldMapTransforms` row be derived?

Generated by `tools/transform.py` from the vendored WDM Stable tables and the
verified stock 3.3.5a baseline. Every number is re-derived on each run; do not
edit this file by hand.

## Scope

54 REVIEW candidates exist because mod-content-manager's `worldMaps[]` contract
requires exactly one `WorldMapTransforms` row per map, and 50 of those candidates
have no WDM-supplied transform. This report asks whether such a row can be
*derived* from the other three WDM tables, and reports what the data supports.

**Short answer: partially. Eight of the ten fields are provable. The tenth,
`NewDungeonMapID`, is not provable for any map with more than one floor.**

## Method and its limits

The four WDM tables are the only client DBCs WDM ships. There is no `Map.dbc`,
no `UiMapAssignment.dbc` and no server-side data in the patch, so no source
outside these tables can settle an ambiguous floor choice. That is a hard limit
on what any derivation can prove, not a gap in the analysis.

Every rule below is tested against the decoded rows rather than assumed. A rule
is reported as *supported* only when every row of its family agrees.

## The table contains two unrelated families

Partitioning on observed values splits the table cleanly: **8 instance-entrance rows** and **5 world-UI region remap rows**, with no row fitting both.

The instance family is the full-coverage shape:

- `RegionBottom/Right/Top/Left` = -20000 / -20000 / 20000 / 20000
- `NewMapID` == `MapID`
- `RegionOffset_X` == `RegionOffset_Y` == 0
- `NewDungeonMapID` names a real `DungeonMap` row of the same map

The UI-remap family (`ID` 2, 3, 5, 7, 8) is a different client feature: tight
partial rectangles, and for map 530 a `NewMapID` of 0 or 1 with large offsets.
These are the rows the world map UI uses to re-page a continuously scaled map.
**All five are stock; WDM added none.** They are not a template for a missing
dungeon transform and are excluded from every rule below.

### What this settles

- `+/-20000` region bounds are universal for the instance family and appear in no
  UI-remap row. 20000 yards is the standard half-extent of a 3.3.5a world map, so
  "the transform covers the whole map" is the rule, not the literal constant.
- `NewMapID` == `MapID` holds for the instance family, but is **not** universal
  across the table: map 530's rows map to `NewMapID` 0 and 1. Quoting it as a
  general rule would be wrong; it is a property of the instance family.
- Offsets are zero throughout the instance family and nonzero in two UI-remap
  rows.
- `NewDungeonMapID` always names a real floor of the same map.

### The direct contradiction

Maps 36 and 369 are structurally near-identical two-floor maps. `Floor` is 1 then 2,
each has a single `WorldMapArea` with `virtualMapId -1` and `dungeonMapId 0`, and in
both the first floor carries one extra chunk with a real tile offset
(27 on Deadmines 166,
-38 on Deeprun Tram 741) while the
second floor holds only the `-10000.0` sentinel. WDM nevertheless chose the **second**
floor for Deadmines (167) and the **first** floor for Deeprun Tram
(741). Two rows that the tables render as equivalent carry opposite
answers, so no function of these tables can reproduce both.

## Why Deadmines selects 167 rather than 166

**The data does not explain it.** Every observable difference between the two
floors, as re-derived from the tables:

| quantity | 166 | 167 **(chosen)** |
|---|---:|---:|
| `Floor` | 1 | 2 |
| chunks | 18 | 11 |
| chunk `field4` values | -10000, 27 | -10000 |
| `field5` | -337.509 | -267.509 |
| `field6` | 35.3335 | 65.3333 |
| `field7` | 39 | 39 |

Neither difference is a defensible "this is where players enter" signal. A
"most chunks" heuristic would pick floor 166, which is the floor WDM did
*not* choose, and the same refutation appears on map 631, where the chosen floor
104 has 2 chunks while floor 107 has
24 and is not chosen. The honest reading is that
`NewDungeonMapID` records the floor an author wired the entrance to, and that fact
is simply not present in any of the four tables. `reports/instance-candidates.md`
treats Deadmines' transform 11 as authoritative because WDM supplies it, not
because this project can reproduce it.

## The narrowest rule the evidence supports

Of the 8 instance-family rows, 2 name a single-floor map
and 6 name a multi-floor map. A `NewDungeonMapID` is
derivable **only for the former**, where the value is forced by elimination. For
those maps the full instance-family rule is completely determined:

```
regionBottom    = -20000.0
regionRight     = -20000.0
regionTop       =  20000.0
regionLeft      =  20000.0
newMapId        = MapID
regionOffsetX   = 0.0
regionOffsetY   = 0.0
newDungeonMapId = the map's only DungeonMap ID
```

Eight fields of the instance family are universal across all 8
rows; the ninth value above is forced only on single-floor maps. On a multi-floor
map the row is well-formed but its `newDungeonMapId` would be a guess, so the rule
does not license publishing it.

## Limits of this conclusion

Three things this analysis cannot establish, stated so they are not over-read:

1. It cannot prove what the client *does* with `NewDungeonMapID`. That requires
   client reverse engineering or PTR observation, neither of which this project
   has done. The finding here is narrower and is about what the DBC rows support.
2. It cannot rule out that a multi-floor `NewDungeonMapID` is discoverable from a
   source outside WDM, such as a `Map.dbc` instance-type field or the server's
   `instance_template` data. Neither is available to this project.
3. It says nothing about whether a correct transform row is *sufficient* for the
   client to display a map correctly. That requires in-game validation.

## Independent blocker: mod-content-manager cannot allocate a transform ID

Even for the 17 single-floor maps, where every value is derivable, the row still
needs an identity, and mod-content-manager will not supply one. This is a separate
issue from the floor-selection finding above and would block the phase on its own.

World-map rows are deliberately excluded from the searching allocator:

```cpp
// src/ContentResourceAllocator.h:14
// Author-declared identity. Only honoured by PlanFixed; the searching
// planners always ignore it and allocate the next free candidate.
std::uint32_t fixedValue = 0;

// src/ContentResourceAllocator.h:46
// A client map row identity is baked into the stock client, so a package
// declares the exact ID it owns instead of searching for a free one.
static ResourceAllocationPolicy FixedRowIdPolicy(std::string const& resourceKind)
{ return {std::move(resourceKind), 1, 0xffffffffu}; }
```

`worldmap.world-map-transforms.id` is routed through that policy at
`src/ContentBuildService.cpp:402`, and `PlanFixed` throws when a request declares no
value (`src/ContentResourceAllocator.cpp:145`). `docs/WORLD_MAP_DBC.md:131` states it
plainly: *"There is no allocator for these rows."*

The consequences are exact:

- A package **must** author-declare the transform ID; there is no
  allocate-next-free path for this resource kind.
- The declared ID is leased **durably** on first build and is "effectively
  permanent"; a retired lease is never handed to another owner.
- CM does validate the choice: `PlanFixed` rejects an ID already present in the
  verified stock baseline or held by another package, so a collision fails the
  build loudly rather than corrupting a row.

So an authored transform is *representable* and would be safely owned, but the ID
would have to be hand-picked and would be frozen into the project permanently.
That is precisely the outcome the phase brief said to refuse rather than work
around, so the implementation path is stopped here. Resolving it needs a decision
from the project owner, not a code change in this repository:

1. Author a fixed ID under an explicitly reserved range and accept permanence, or
2. Upstream a change to mod-content-manager giving world-map rows a real allocator,
   or
3. Restrict published maps to those where WDM supplies the transform, i.e. the
   three already published.

Option 1 is the only one available without touching mod-content-manager, and it is
a policy decision about permanent public identity, not a technical question.
